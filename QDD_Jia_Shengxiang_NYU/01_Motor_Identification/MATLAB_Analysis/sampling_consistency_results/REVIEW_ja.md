# サンプリング周期の不整合：PD＋chirp入力の検査

2026-09-17。新規check_sampling_consistency.mをMATLAB R2026aで実行、終了コード0。
最終出力の時刻図・FRF比較図を目視確認。元CSV、実験スケッチ、既存の結合FRFは変更していない。

## 結論

固定2 kHzは記録と一致せず、平均記録レートへの修正は必要。
直前の個別同定・結合プログラムでは既に各CSVの平均記録レートを使っているので、その補正は反映済み。
平均レート補正後も記録の非等間隔性は残るが、現在のミリ秒タイムスタンプから正確な約0.5 msのサンプル時刻を復元することはできない。
時刻平均化・1 kHz等間隔化は今回は感度検査として扱い、より正しい結果として自動採用しない。

## 1. 三種類の「周期」を区別する

1. Teensyが指令を更新する周期。
2. モータードライバが内部で計測し、CANで返す周期・遅延。
3. Teensyが受信・CSV出力する周期。

今回CSVから直接調べられるのは主に3。CSV行数から算出した約506 µsは平均記録周期であり、モーター内部の計測周期が506 µsと確定したわけではない。

## 2. 実測時刻による結果

| 項目 | 低周波2 Nm | 高周波5 Nm |
|---|---:|---:|
| 平均記録周波数 | 1977.105 Hz | 1975.921 Hz |
| 平均記録周期 | 505.790 µs | 506.093 µs |
| 固定2 kHzによる終端時刻の不足 | 3.480 s | 1.3725 s |
| 固定2 kHzによる周波数尺度の過大評価 | 1.158% | 1.219% |
| 平均レートで作った時刻との差の最大絶対値 | 23.586 ms | 12.819 ms |
| 1 ms超のタイムスタンプ間隔 | 0 | 1箇所・4 ms |

高周波CSVの4 ms間隔は記録経過70.945～70.949秒、次行番号140197。
失われたサンプル数やCAN・ログのどちらが原因かは確定できない。
約2 kHzの記録をmillisで出しているため、同じ時刻値の行があること自体は異常ではない。
平均レートとの時刻差13～24 msは長時間の累積した記録時計のずれ。単一サンプルのジッタや入力・出力間遅延が13～24 msという意味ではない。

## 3. FRFへの影響

同じPD＋chirp入力・実測角度について、次を比較した。

- 固定2000 Hzで行を等間隔と仮定。
- 全体の平均記録レートで行を等間隔と仮定（現在の結合解析の方式）。
- 同じミリ秒時刻の入力と出力をそれぞれ平均し、1000 Hzの時刻グリッドへ変換。

3番目はタイムスタンプ間隔が1 msを超える箇所で区間を分け、欠けた時刻を補間でつながない。
区間ごとにWelchスペクトルを計算し、寄与窓数で重み付けして統合した。クロススペクトルはtfestimateの位相規約に統一。
窓時間長は約2.07秒でそろえた。元の行方式は4096点、1 kHz方式は約2072点。
区間の分割・トレンド除去・窓配置・ビン平均化も変わるため、この比較は時刻だけの純粋な因果効果ではない。
特に1 kHz化は厳密な帯域制限フィルタ付き再サンプリングではなく、ミリ秒時刻ビン平均による近似。高周波雑音の折り返し等も保証できない。

平均レート方式との差（両方式のcoherence>=0.9の点、対数周波数グリッド）：

| 比較方式 | 低周波 振幅RMS | 低周波 位相RMS | 高周波 振幅RMS | 高周波 位相RMS |
|---|---:|---:|---:|---:|
| 固定2000 Hz | 0.191 dB | 0.109° | 0.226 dB | 0.462° |
| 時刻グリッド1000 Hz | 0.0043 dB | 0.0037° | 0.0289 dB | 0.287° |

時刻グリッド方式の高周波側は350点中339点で上記基準を満たした。低coherenceの11点は統計から除いたが図には残している。
約48 Hz付近のcoherence低下と高周波での悪化が見られる。4 ms間隔で分割した時刻がチャープのその周波数付近に対応し得るため、
区間端・窓配置と時刻平均化の影響を分離できない。「実機の48 Hz応答が異常」「時刻方式で正しく補正された」とは判断しない。

## 4. 現行Arduinoコードに見られる原因候補

motor1ak80.inoでは：

- `if (txTimer >= 500) { txTimer = 0; ... }`。ループが500 µsを超えて実行された際の超過分を捨てるため、位相の遅れが積み上がり得る。
- `readCANMessages()`を周期判定前に呼び、受信処理内で多数のSerial.printを実行する。処理時間やUSB側の状態が周期判定に影響し得る。
- CSVは制御周期ごとではなく受信イベントごとに出る。そのため指令周期と記録周期が一致する保証はない。
- `millis()`で記録し、約500 µs周期に対して時刻分解能が粗い。
- 現行スケッチと取得時コードにはチャープ条件等の相違がある。これらはコード上の問題候補であり、過去ログの全原因を確定したものではない。
- Teensy USB SerialではSerial.beginの数値だけで物理転送帯域を決めつけない。実際の転送・バッファ挙動を計測する必要がある。

## 5. 実験プログラムで直すべき設計

次回取得では以下をそろえる。

1. 制御更新、CAN受信、ログ転送を分離。受信・周期制御内で長い文字列出力をせず、構造体のバッファへ保存する。
2. 固定の予定時刻を積み上げるスケジューラまたはハードウェアタイマを使う。超過時に古い指令を高速で連続送信するcatch-up動作は避け、取りこぼした周期数を記録する。
3. `micros()`の指令更新時刻、送信要求時刻、CAN受信時刻、記録時刻を区別して保存する。送信要求時刻は実際のCAN線上送信時刻と同じとは限らない。
4. command_index、feedback_index、フィードバック経過時間、CAN書き込み失敗数、周期超過数、ログ欠落数を保存する。
5. 指令送信と状態計測の同期関係を確認し、指令周期・記録周期・ドライバ計測周期を別々に測定する。
6. 元の物理量と時刻を保存したまま、解析側で有効区間の切り出し・等間隔化・欠測除外を行う。

今回は実験スケッチの変更や実機検証は行っていない。既存データで判断できる限界と、次の実装要件までを整理した。
