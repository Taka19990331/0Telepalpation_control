# Teensy 4.1 起動・開始診断結果

実施日: 2026-11-02 (JST)  
検証ソース: trans_ctrl_test2_startup_diag  
元の trans_ctrl_test2 ソースは変更していない。

## 実機環境と方法

- Arduino CLI 1.5.1、Teensy platform 1.62.0でSD有効・無効の両方をビルドした。最終のSD有効版を書き込み、Teensy Loader経由のアップロードは正常終了した。
- teensy_portsがTeensy 4.1をCOM3として検出した。通常権限のCOM3オープンはAccess deniedだったため昇格実行で取得した。実行中プロセスにArduino Serial Monitor、Teensy Monitor等は見つからず、ポート占有は観測していない。
- Teensy 4.1上でSDをSD,OKとして認識した。AK80-8 KV60の電源はOFFのまま、モータ駆動試験は行っていない。
- final6_serial.logには最終ファームの起動・コマンド・停止・SD検証ログを保存した。final6_trials.csvは最終3試行、baseline_trials.csvは元版3試行のホスト側記録。
- 最終DコマンドはTRANS_END,TC0115.CSV,23で完了し、レコードCRC、連番、終端レコード、rows/status情報を含むログ全体の検証に通った。
- ポート番号を指定しない期限付き再接続も確認した。teensy_portsからCOM3を再検出し、追加の1試行とD検証が成功した。

baseline_trials.csvのS送信からSAVEDまでの値には、SAVED受信後にSTATUS出力を読む時間（約200 ms）が含まれる。最終版はSAVEDを検出した時点を記録するため、この2つのホスト側所要時間は直接比較していない。

## 修正内容

検証用コピーだけに次を追加・修正した。

1. 起動時のSerial.begin()は、USBシリアル接続後に呼ぶようにした。TeensyのUSB Serial実装は未接続時に最大約2秒待つため、その待ちをsetupから外した。起動計測はUSB接続後に出し、リセット直後のログ欠落を避ける。
2. 起動時の最大10,000件の個別sd.exists()探索をやめ、SDのルートディレクトリを一度列挙してファイル番号のビットマップを作る。S開始時の空き番号探索はメモリ内で行い、作成は従来どおりO_EXCLを使う。
3. S開始時にFlexCAN_T4オブジェクトをセッション境界で再初期化し、前セッションの保留TX/RXキューを破棄した。バス、速度、メールボックス、フィルタ、割込み優先度は同じ設定で再適用する。
4. Sの拒否理由、SD探索・作成・メタデータ・sync時間、CAN再初期化・Enable・ゼロ指令の受理、active移行、停止理由、ログfinalizeとsync時間を出力する。
5. startRequestからactiveへ移るまでの最大500 µsの間にONが届く競合を修正した。要求済みセッションと安全条件を満たす場合にON設定を受理するが、制御出力は従来どおりactive状態かつ有効フィードバックがある場合だけ許可される。

control_algorithm.h、control_config.h、position_direction.hのSHA-256は元版と検証版で一致した。RFOB、摩擦FF、LPF/Q、ゲイン、トルク制限、タイムアウト、安全停止の条件は変更していない。

## 計測結果

| 項目 | 計測前の診断版 | 最終版 |
|---|---:|---:|
| setup内 Serial.begin | 2,000,801 µs | 0 µs (setup外へ移動) |
| CAN初期化 | 31 µs | 32 µs |
| SD mount +探索 | 91,119 µs (mount 10,978 +探索 80,141) | 16,574 µs (mount 10,978 +列挙 5,594) |
| Timer初期化 | 1 µs | 0 µs |
| 計測したsetup所要時間 | 2,091,952 µs | 16,607 µs |

同じボード・同じSDでの計測段階比較では、setup時間を約2.075秒（約99.2%）短縮した。計測前版のready_elapsed_usにはホストがシリアル接続するまでの時間も混ざるため、表では各setup段の所要時間を合計して比較した。

最終3回の内部S処理は、SaveData::start()が5,275–5,281 µs、空き番号探索が2–3 µs、ファイル作成が3,978–3,986 µs、メタデータが89–90 µs、開始時syncが1,202–1,205 µsだった。active移行はS受信から5,338–5,511 µs。ホスト側S送信から応答までの12.7–23.1 msは、シリアル監視の10 msポーリングを含む。

停止後のログfinalizeは1,739–1,740 µs、終了syncは988–990 µs。S送信からSAVED受信までは31.2–39.4 msだった。

## 反復試験結果

最終版の連続3試行と、ポート自動再検出を含む追加1試行で次を確認した。

- S開始受理: 4/4
- ON要求受理: 4/4 (ON_ACCEPT)
- SD終了・sync成功: 4/4 (SAVED, status 2)
- 次のSの受理: 4/4
- Dによるログ検証: 2回成功 (各23行、TRANS_END)
- SD書き込み失敗: 0
- 予期しない再起動・ハング: なし

元版の3試行では、1回目に24件のCAN write受付後、送信キューが満杯になり、2・3回目は古いCANキューが残ってEnable送信に失敗した。最終版ではセッションごとにCANを再初期化し、3/3回のSとON要求を受理した。

## 制約・未検証事項

モータ電源OFFではCAN受信が0件で、送信キューが16件まで詰まり、最初の送信失敗時のフィードバック経過時間は約11 msだった。停止理由は3回とも2（CAN TX write失敗）で、100 msフィードバックタイムアウト理由6には到達していない。CAN送信失敗時の安全停止は有効のままにしたため、指定の100 msタイムアウト単独の再現・合格判定は未完了。

ON_ACCEPTとCANライブラリのwrite受付はソフトウェア上の受理を示す。モータ電源投入時のCANフレーム到達、ドライブ側Enable成立、実フィードバック、実トルク出力は確認していない。

SD上の既存ファイルは約100件の状態で列挙・欠番処理を確認した。10,000件すべてが存在するカードでの負荷試験は未実施。
